# Add pagination to vehicle/driver "all" efficiency lists

## Goal
The "All vehicles" and "All drivers" tables in the 004.008 efficiency
widgets currently render every row in one unbounded table. Paginate both
to 5 rows at a time with controls to see more; the "worst 5" lists are
unaffected.

## Acceptance criteria
- [ ] "All vehicles" table shows 5 rows at a time with pagination controls.
- [ ] "All drivers" table shows 5 rows at a time with pagination controls.
- [ ] The two widgets' pagination state does not collide when both are on
      the dashboard at once.
- [ ] Feature tests confirm exactly 5 items render per page when more than
      5 exist, and the total count is still correctly reported.
- [ ] Existing "worst 5" sections and FMA-failure/empty-state behavior are
      unaffected (existing tests for those still pass).

## Permitted paths
- `illima-dashboard/app/Filament/Customer/Widgets/VehicleEfficiency.php`
- `illima-dashboard/app/Filament/Customer/Widgets/DriverEfficiency.php`
- `illima-dashboard/app/Traits/InteractsWithCustomerFmaData.php`
- `illima-dashboard/resources/views/filament/customer/widgets/vehicle-efficiency.blade.php`
- `illima-dashboard/resources/views/filament/customer/widgets/driver-efficiency.blade.php`
- `illima-dashboard/tests/Feature/VehicleEfficiencyWidgetTest.php`
- `illima-dashboard/tests/Feature/DriverEfficiencyWidgetTest.php`

## Prohibited changes
- Do not change how the "worst 5" lists are computed or ranked.
- Do not modify the staff panel.

## Verification
```bash
cd illima-dashboard && php artisan test --filter=EfficiencyWidgetTest
```

## Manual verification (required — this chunk touches a Filament/Livewire UI)
- [ ] Open the customer dashboard in a real browser with more than 5
      vehicles and more than 5 drivers in the selected range.
- [ ] Confirm the "All vehicles" table shows exactly 5 rows and visible,
      clickable pagination controls.
- [ ] Click to the next page: confirm the table actually updates to show
      different rows (not a no-op, not a full-page reload, not a visual
      glitch), and the total-count text still reads correctly.
- [ ] Repeat for "All drivers".
- [ ] With both widgets visible on the same dashboard load, paginate one
      to page 2 and confirm the other widget's pagination is unaffected.
- [ ] Confirm the "worst 5" sections still look and behave exactly as
      before.

## Notes
This is the one criterion the real 004.013 attempt lacked up front (it
was added to the ticket's checklist only *after* the manual browser check
failed and the work was reverted — see the real ticket file's Status
section and its `failed-attempt/README.md`). The 14-tests/48-assertions
automated suite passing was real and correct as far as it went; it simply
never exercised whether clicking a pagination link in an actual browser
did anything, because nothing in the chunk asked anyone to check. Had
this Manual verification section existed as a required, non-optional part
of the chunk *before* implementation started, it would have caught the
exact failure at the same point it was actually caught (a human clicking
around a real browser) — just as a planned, expected step instead of an
after-the-fact surprise discovered by the client/user.

This does not solve the underlying gap PLAN.md tracks (an automated
UI/browser verification tier, deferred further out) — it only makes the
existing, always-available manual check a structural, required part of
the chunk instead of something that depends on a human remembering to do
it and to state it up front.
